The one-sentence insight

Routing granularity carries accuracy; KV content density only buys speed.
ExpertPlusPlus keeps Flat's fine 4:1 router (64 index tokens) but halves the attention matrix by attending to 8:1-compressed KV blocks. A naive "ExpertFlat" (8:1 on both axes) lost accuracy (0.1102) because the router got coarser too.

What "column" means here

Every query position runs a softmax over a set of key columns, then takes a weighted sum of the corresponding values. The number of columns is the single biggest cost driver:

2

Full S×S score matrix + causal mask — this is the O(S²) cost

Fig. 3 — Every query attends to every previous key. (Grid is schematic — real matrix is 256×256 per head.)
Where the scores come from — one cell at a time

Each cell in the grid is a scaled dot product between one query vector and one key vector. In code (attention.py, _attend):

attn_weights = matmul(q, kᵀ) · (head_dim)⁻¹ᐟ²   =   q · k / √32

Concretely, for query position i and key position j, the score is the sum over the 32 channels:

score(i, j) = Σₘ q[i, m] · k[j, m] / √32

So the row of the grid is fixed by the query (which position is asking), and the column is fixed by the key (which position is being asked about). The / √32 is a stabilizer: it keeps the dot products from growing with the vector length, so the softmax in Step 3 doesn't saturate. The causal mask then overwrites the upper triangle (future columns) with −∞.

The worked example below (Step B) does exactly this arithmetic by hand for a 2-dim world: q₂ = [−0.4, 0.9] dotted with each key gives −0.15, 0.75, 0.29, −0.45.

The matmul shapes — before and after

Here is exactly what the matrix multiply consumes and produces, with the contraction dimension (the one that sums away) highlighted:

tensorshapemeaning
q[B, 4, 256, 32]4 heads × 256 queries × 32 dims
k[B, 4, 256, 32]4 heads × 256 keys × 32 dims
kᵀ (transposed)[B, 4, 32, 256]swap last two axes → keys become columns
scores = q · kᵀ[B, 4, 256, 256]256 queries × 256 keys — the 32 dims summed away

The rule: matmul(A, B) contracts the last axis of A with the second-to-last axis of B. Here q [B,4,256,32] × kᵀ [B,4,32,256] → the shared 32 is the contraction dim, leaving [B,4,256,256]. Each output cell [b,h,i,j] = Σₘ q[b,h,i,m]·k[b,h,j,m] — the dot product of query i with key j.

The / √32 scaling happens after the matmul, element-wise, so it doesn't change the shape.

3

Softmax over the 256 columns → weighted sum of values

probs = softmax( scores + causal_mask , dim = −1 )   attn_out = probs · v

Row-normalized: each query's attention weights sum to 1 over its 256 allowed keys. The output is [B,4,256,32]. Then RoPE is rotated back with −sin (undoing the query rotation so the output stays in an unrotated basis before the O projection).

4

Grouped O projection → hidden size

Fig. 4 — Normal uses o_lora_rank = 128 (same as Flat; EPP halves it to 64).
How the grouping works — heads stay separate, then merge

The input is attn_out [B, 4, 256, 32] — 4 heads, each a 32-dim vector per position. The trick: each head is projected by its own small matrix, not all heads by one big matrix. In code (attention.py, forward):

grouped = attn_out.transpose(1,2).reshape(B, S, 4, 32)  →  o_a_proj  →  flatten(2)  →  o_b_proj

Step by step:

stepshapewhat happens
attn_out[B, 4, 256, 32]4 heads × 32 dims
transpose + reshape[B, 256, 4, 32]reorder so the 4 heads sit on their own axis
o_a_proj (Grouped)[B, 256, 4, 128]each of the 4 heads: 32 → 128, independently
flatten(2)[B, 256, 512]concatenate the 4 × 128 back into one 512-dim vector
o_b_proj[B, 256, 128]Linear 512 → 128, back to hidden size

So grouping = 4 separate 32→128 projections (one per head) instead of one 128→512. The GroupedLinear class implements this as a single nn.Linear(512, 32) whose weight is reshaped to (4, 128, 32) and applied per-group with a batched matmul — so it is one parameter tensor of 512 × 32 = 16,384 params, not 4 separate 512×32 matrices.

Why do it this way? It lets each head keep its own output subspace (no cross-head mixing in the low-rank step), while sharing the single o_b_proj that merges them. EPP shrinks the per-head rank from 128 → 64, cutting this weight from 16,384 → 8,192 params — the single biggest parameter saving.

Why it is slow

  • Quadratic: the score matrix is S×S per head → 256×256 = 65,536 cells per head at S=256.
  • No reuse: every query sees every key; there is no compression and no caching of history.
  • Yet also the most accurate baseline — it never loses information, hence the lowest val MSE (0.1083).

🌿 Flat (CSA V4) — two-series compressor + flat indexer

Stage 4 — what exactly is being compressed? (k, not q)

The compressor runs on the key/value stream only — the k = v tensor from stage 3, shape [1, 256, 32]. The query q is never compressed; it stays at full 256 positions and is used later (stage 7) to ask which compressed blocks to look at.

In code (attention.py, _flat_two_series_compress):

comp_kv = kv_proj(hidden_states[:, :usable])  →  [B, 64, 4, 2·32]

Each of the 256 k/v tokens is projected to 2·32 = 64 channels — a first half (the "fresh" content) and a second half (the "carried" content). These halves are what get placed into the 8 slots of each block. So the answer to "is it k, v, or q?": it is k = v (tied), and q is untouched.

Stage 6 — where does the 32 dimension come from?

The 32 is not invented by the compressor — it is the head dimension head_dim = 32, the same width as every key/value vector. The compressor never changes the per-vector width; it only changes how many vectors there are (256 → 64).

stageshapewhat changed
3 · kv_proj[1, 256, 32]256 tokens, each 32-dim
4 · slots[64, 8, 32]64 blocks × 8 slots, each slot still 32-dim
5 · softmax[64, 8, 32]weights over the 8 slots, per channel
6 · weighted sum[1, 64, 32]8 slots → 1, width stays 32

The 2·dim in stage 4 is a temporary doubling (fresh + carried halves) that the softmax recombines; the output width is back to dim = 32. So [1, 64, 32] = 64 blocks × 32-dim keys, ready to be dotted with the 32-dim queries.

Stage 8 — 16 blocks per query, but 97 columns? The math

The router picks 16 blocks per query, but the dense attention still runs over all 97 columns. These are two different things:

97 columns = 32 (sliding window) + 64 (all blocks) + 1 (sink)

The router's 16 choices are not used to shrink the matrix. Instead, they become a mask: the 16 chosen blocks get a score of 0, and the other 48 blocks get −∞ (so their softmax weight is exactly 0). The GEMM still computes all 97 columns — on CPU, a dense GEMM over 97 columns beats a per-query gather+bmm even though only ~16 blocks are "used".

So the 16 is the routing budget (which history matters), and the 97 is the compute width (what the matmul actually touches). They are decoupled by design.

The two-series compressor (the core idea). Consecutive blocks overlap by one window: each block's first half of slots carry the previous window's tokens, the second half carry the current window's tokens. A per-dimension softmax over 2m=8 slots decides, for each output channel independently, whether to trust the carried-over memory or the fresh token. This is not pooling — it is learned, channel-wise, position-aware gating.

The compressor, step by step (m = 4 for Flat)

Fig. 5 — The two-series overlap: block w mixes the first halves of window w−1's tokens (gold, the carried memory) with the second halves of window w's own tokens (green). Each of the 32 output channels independently softmaxes over the 8 slots. RoPE is applied at the block start position (4w).

⚠️ The key insight — this 8-slot sum runs ONCE per sequence, not once per query

This is the part that's easy to miss. The compressor's weighted sum is amortized: it is computed one time for the whole sequence, before any query is processed. Every one of the 256 query positions then reuses the same 64 compressed blocks.

Normal (no compression)Flat (compressed)
What each query attends to256 raw keys32 window keys + 16 selected blocks
Per-query dot products25632 + 16 = 48
Compression worknone64 blocks × 8 slots = 512 sums, once
Total dot products (256 queries)256 × 256 = 65,536256 × 48 + 512 ≈ 12,800

So the compression is not "8 times the work per query" — it's a one-time setup cost that shrinks the per-query attention from 256 columns to 48. The 8-slot sum you traced above is done once for block 1, and the result compressed₁ is then shared by all 256 queries. That's the whole point: pay the compression once, attend cheaply many times.

In the tiny example: 8 tokens → 2 blocks. The 8-slot sums run twice (once per block). Then each query attends to just 2 blocks instead of 8 raw tokens. The savings grow with sequence length — at S=256 it's 65,536 vs ~12,800 dot products.

What happens to each block, and how they're combined — the full pipeline

You asked: after splitting into blocks, what happens to each one, and how are they combined again? Here is the complete journey of the 8 tokens → 2 blocks → final output, in order:

#stagewhat happensresult
1Split8 tokens grouped into 2 windows of 4 (W₀ = t₀…t₃, W₁ = t₄…t₇)2 windows
2Projecteach token → kv_proj → 2·dim vector: [first half | second half]8 × 2-dim
3Assemble slotsblock 1's 8 slots = first halves of W₀ (carried memory) + second halves of W₁ (fresh)8 slots
4Gateper-dimension softmax over the 8 slots → 8 weights per channel8 weights × 2 dims
5Weighted sumΣ slot_value × gate_weight → one 2-dim vectorcompressed₁ = [0.625, 0.5625]

7Repeatsame for block 0 → compressed₀2 blocks total

The crucial point is steps 1–7 happen once (amortized), and steps 8–10 happen per query but on the tiny 2-block set. The blocks are not re-combined into 8 tokens — they stay compressed, and the query just attends to the compressed summaries. That's the entire trick.

"Does it always split into 2?" — No. The 2 is the two-series, not the block count

This is the most common confusion. The 2 in the diagram is the two-series: every block has 2m slots = m carried-over + m fresh. It is a constant — it never changes with sequence length.

The number of blocks is a different number: n_win = S ÷ m. It grows with the sequence. The example above used 8 tokens with m=4, so it happened to make 2 blocks — but that's a coincidence of the toy size, not a rule.

sequence length Swindow mblocks n_win = S/mslots per block
8422m = 8
16442m = 8
32482m = 8
256 (real config)4642m = 8

So: slots-per-block stays 8 forever (that's the "two-series"), but the block count grows with S. More tokens → more blocks, each still just 8 slots. The compression ratio is always m:1 (here 4:1), so 256 tokens → 64 blocks.

From scratch — 16 tokens → 4 blocks, the full input flow

Let's trace 16 raw tokens (m = 4) end-to-end, so you see exactly how the input flows. The windows are W₀ = tokens 0–3, W₁ = 4–7, W₂ = 8–11, W₃ = 12–15.

Each block then does the same 3 steps as before: (a) per-dimension softmax over its 8 slots, (b) weighted sum → one 32-dim vector, (c) RMSNorm + RoPE at the block's start position. Result: 4 compressed vectors.

Then the router: 16 tokens at 4:1 → 4 index tokens, each covering [4t, 4t+3]. Identity map → index token t is block t. A query picks its top-k (here k=4, all of them), and attends over window + 4 blocks.

Compare with the 8-token example: same 8 slots per block, but 2 blocks instead of 4. The machinery is identical — only the block count scales with S. At the real S=256 you get 64 blocks, and each query attends to 32 window + 16 selected blocks = 48 columns.

What are the "32 window" and the "1 sink"? (the other two parts of the 97)

You already know the 64 blocks: compressed 4:1 summaries of the whole sequence. The other two pieces come straight from _attend:

the 32 windowthe 1 sink
codesw_k = kv[:, :, -32:, :]self.sinks = nn.Parameter(torch.zeros(4))
what it isthe last 32 raw key tokens before the query — uncompressed, full resolution4 learnable scalars (one per head), broadcast into ONE extra column

So 96 real keys + 1 dump column = 97 softmax columns; after softmax the sink is sliced off and probs · total_v contracts the 96 real columns back to [B,4,256,32]. The window is always attended — the router never touches it; the blocks are what the router picks.

Why does the sink exist? — softmax is forced to spend 100% of its probability

Softmax never leaves money on the table: whatever columns you give it, the probabilities always sum to 1. If a query matches nothing well, its 48 unmasked logits are all small — yet softmax still hands out 1.0 total, so the output becomes a near-uniform blend of every value. The sink is a place to throw probability away instead.

Toy numbers, one head, learned sink logit s = 0.5. Three real columns:

query strengthreal logitsprobs WITHOUT sinkprobs WITH sinksink takes
strong match[5.0, 4.0, 3.0][0.665, 0.245, 0.090][0.660, 0.243, 0.089]0.7% — barely matters
weak match[0.5, 0.3, 0.1][0.402, 0.329, 0.269][0.287, 0.235, 0.192]28.7% — dumps a quarter of the budget

The sink is a learned confidence gate: when a query finds a clear winner it's ignored; when a query is uncertain it automatically swallows mass (the denominator grows relative to the weak real logits). After softmax, scores = probs[..., :-1] deletes the sink column, so that mass simply vanishes from the weighted sum — the output shrinks, and the downstream layers read "small output = low confidence". Without the sink, the uncertain query would be forced to average all 96 values uniformly. Note the relative ratios of the real columns are unchanged — softmax only rescales — so the sink can't hurt the ranking, it only modulates overall confidence. The sink has no key/value of its own: it's purely a normalization device, costing just num_heads = 4 parameters.

"Doesn't the sink leave the probs basically the same?" — yes, and that's the point

Sharp question, and the answer is yes: the sink does not change which keys get attended. Softmax is shift-invariant, and the sink is just one extra column, so every real probability is multiplied by the same scalar:

output = (1 / (1 + es − log Σ elj)) × Σi eli vi

The ratios p₁ : p₂ : p₃ are identical with or without the sink. So what does it actually change? Only the magnitude of the output vector — a per-query, per-head gain:

strong match (Σ elj huge)weak match (Σ elj small)
the factor≈ 1 → no effectshrinks → output scaled down
what it reads as"confident, pass it through""unsure, shrink your vote"

Why bother, if it's just a scale? Because the scale is per-query and per-head and nonlinear — it depends on that query's own match quality. A linear O projection can only apply a fixed weight; it can't know "this particular query was a weak match." The sink gives the model that per-query nonlinearity for just 4 parameters. The residual stream reads "small output = low confidence."

Honest caveat: it's a mild effect, not the main mechanism — the model could partly compensate in the O projection. It's a cheap, stable regularizer, not the reason CSA is fast or accurate. The speed/accuracy story is the window + blocks + router; the sink is a small confidence knob on top.

"Isn't scaling down when unsure the same as just having a smaller output?" — the one thing it unlocks

This is the crux, and the answer is: plain softmax attention literally cannot output less than a full weighted average. Its weights always sum to 1, so the output always sits inside the convex hull of the values — it has the same "energy" as the values it averages, no matter how unsure the query is. The sink is the only mechanism that lets the output be a sub-convex combination (weights sum to < 1), i.e. have less magnitude than the values it's averaging.

objectionwhy it's not the same
"Couldn't the O projection just learn a scale?"O is a fixed linear map applied to every query identically. It can't shrink this query and not the next. The sink is per-query.
"Couldn't the values just be small?"The KV blocks are shared by all 256 queries. Shrinking them shrinks every query. The sink shrinks one query only.
"Couldn't the model just not attend?"Softmax forces it to attend — weights sum to 1. The sink is the only escape hatch that lets the sum drop below 1.

So the point isn't "scale down" per se — it's that the sink is the only per-query, per-head, nonlinear gain in the whole attention path. It lets a low-confidence query withdraw its vote instead of being forced to average noise into the residual stream. That's a real degree of freedom that a plain softmax attention doesn't have — and it costs just 4 parameters.

Still honest: it's a small degree of freedom, and the model could partly mimic it elsewhere. But it is not redundant with anything else in the architecture — no other component can produce a per-query sub-convex output.

"So it scales down the output until some queries withdraw their votes?" — almost, one fix

Your core idea is right — low-confidence queries end up contributing less to the residual stream. But the mechanism is not "some queries opt out." The sink is one scalar per head, shared by all 256 queries of that head, so it applies a single continuous gain to every query — and that gain is smaller for weak matches, ≈ 1 for strong matches:

outputq = (1 / (1 + es − log Σ eljq)) × Σi eliq vi
strong matchweak match
gainq→ 1 (pass through)shrinks (vote withdrawn)
effectconfident query contributes fullyuncertain query contributes less

So it's a smooth, per-query gain — not a discrete "some queries withdraw." The scalar s is learned once per head (the model picks a "skepticism level" per head), but the gain is still per-query because it depends on that query's own logits. Every query gets scaled by its own gainq; confident ones ≈ 1, unsure ones < 1.

OK, but what is the MAIN point? — abstention, not gradients

One sentence: the sink lets attention output "nothing" when it's unsure, instead of being forced to inject a full-strength average of noise. It's an abstention mechanism — and here's why that matters.

Every query's output lands in the residual stream (x + attn_out). Without a sink, a weak query is forced to emit a full convex combination (Σp = 1): a near-uniform blend of the 16 selected blocks + 32 window values — i.e. random noise written into the residual at every unsure position. With a sink, the same weak query emits ≈ 0, so the residual passes through unchanged. The output magnitude becomes a clean, readable signal: "how confident is this layer about this position?"

your questionhonest answer
Main point?Abstention — output "nothing" when unsure, instead of forced noise injection
"When most outputs have the same vote confidence"?All-equal logits → uniform softmax → output = plain mean of all values (a noise blob). The sink scales that mean down: same shape, smaller magnitude — the network learns "flat distribution = abstain"
Is it for gradients?No. Softmax already gives clean gradients to all logits; the sink fixes nothing there. The only gradient side-effect: weak queries produce proportionally smaller gradients to the KV values — an implicit per-query learning-rate. A stability bonus, not the goal.
Where does it come from?The CSA paper: with 48 of 64 blocks masked to −∞, a query with no good match would otherwise be forced onto its selected blocks anyway. The sink is the escape hatch.
How much does it matter?Mild but real — 4 parameters, calibration/stability. It is not the speed/accuracy engine; that's the window + blocks + router.

Concretely, if all N unmasked logits are equal to l, the no-sink output is mean(v); with sink s it becomes (N·el / (N·el + es)) × mean(v) — the same average, scaled by a factor < 1 that shrinks as the match gets weaker. Downstream can then treat "small attention output" as "this position had no reliable information" — something plain softmax attention simply cannot express.

Stage 6 — what does "shared-Q" mean?

In Flat, the router uses a separate query projection: idx_q_proj takes the low-rank query residual and produces a dedicated routing query q_idx. In EPP, that projection is deleted entirely (del self.idx_q_proj), and the router reuses the main attention query q — already RoPE'd and normalized — as its routing query.

q_idx = q   (the same [B, 4, 256, 32] tensor that attends)

This works because EPP requires head_dim == index_head_dim (both 32), so the main Q's 32-dim vectors are shape-compatible with the 32-dim index tokens. The router then scores all 64 index tokens:

scores = q · compressed_idxᵀ · ReLU · (32)⁻¹ᐟ²  →  [B, 4, 256, 64]

It's a compute-only saving: one fewer projection (and its params) with no routing-quality loss, because the main Q is already a good routing signal.

Stage 7 — what does "dedupe" do, and how?

The router picks 16 index tokens (4:1, each covering 4 positions). But the KV blocks are coarser (8:1, each covering 8 positions). Two adjacent index tokens map onto the same KV block:

index token t covers [4t, 4t+3]  →  KV block ⌊t/2⌋ covers [8·⌊t/2⌋, 8·⌊t/2⌋+7]

So tokens 2j and 2j+1 both map to block j. If the router picks both, they collapse to one block — that's the dedupe. In code (_postprocess_topk):

blocks = top_k_indices // 2   # integer division collapses pairs

16 tokens → at most 16 blocks, but usually fewer because pairs collide. The result is a set of ≤16 distinct KV blocks per query.

Stage 7 — how do 64 index tokens map onto 32 blocks? The math

This is the heart of the decoupled design. The index tokens and KV blocks live on different grids, and the mapping is a simple integer division:

index token tcovers positionsKV block ⌊t/2⌋block covers
0[0,3]0[0,7]

Each 8:1 block j is the union of index tokens {2j, 2j+1}. So the router's fine 4:1 decision (which 4-token span matters) is preserved at scoring time, but the content it reads is the coarser 8:1 block. The router keeps Flat's precision; the KV density is halved. That's the whole trick.

Stage 8 — 16 blocks per query, but 49 columns? Same as Flat

Identical logic to Flat, just smaller numbers:

49 columns = 16 (window) + 32 (all KV blocks) + 1 (sink)

The router's ≤16 chosen blocks get bias 0; the other 32−16 blocks get −∞ (softmax weight exactly 0). But the GEMM still runs over all 49 columns — dense, not sparse. The 16 is the routing budget; the 49 is the compute cost. EPP's win over Flat is that this is 49 columns instead of 97 (window 32→16, blocks 64→32).

The design bet: keep the router exactly as fine as Flat (64 index tokens, 4:1) but make the KV content 2× coarser (32 blocks, 8:1). The router's precision — the ability to distinguish which 4-token span of history matters — is what preserves accuracy; the KV density only affects the size of the dense attention GEMM. Then recover speed from three compute-only cuts: shared-Q routing, slim O (rank 64), window 32→16.

"Does it always split into 2?" — EPP has TWO different block counts

EPP is the decoupled design, so it has two granularities running at once. The "2" you see is again the two-series (2m slots per block) — a constant. But the block counts differ between the two compressors:

compressorrateblocks = S ÷ rateslots per block
KV content (comp_kv)8:1256 ÷ 8 = 322m = 16
Routing index (comp_idx)4:1256 ÷ 4 = 642m = 8

So EPP runs two compressors in parallel: a coarse 8:1 one that makes the 32 KV blocks the query attends to (fast), and a fine 4:1 one that makes the 64 index tokens the router scores (accurate). The two-series "2" is baked into both — it's the overlap, not the count.

From scratch — 16 tokens, the decoupled flow (KV 8:1 + index 4:1)

Let's trace 16 raw tokens through EPP's two compressors. This is where EPP differs from Flat: the KV blocks and the index tokens are different sizes.

① KV compressor (8:1): 16 tokens → 2 KV blocks, each covering 8 positions. Block 0 = tokens 0–7, block 1 = tokens 8–15. Each block has 2m = 16 slots (8 carried + 8 fresh).

② Index compressor (4:1): 16 tokens → 4 index tokens, each covering 4 positions. Token 0 = [0,3], token 1 = [4,7], token 2 = [8,11], token 3 = [12,15]. Each has 2m = 8 slots.

index token tcoversmaps to KV block ⌊t/2⌋block covers

So the router scores 4 fine index tokens (precise routing), but they address only 2 coarse KV blocks (fast attention). Two index tokens share one KV block — that's the decoupling. The query attends over window + 2 blocks, not 4.

At the real S=256: 64 index tokens (fine routing, keeps accuracy) → map onto 32 KV blocks (coarse content, fast). The router precision is what Flat has; the attention width is what ExpertFlat has. That's the whole EPP trick.

10 · What was tried and failed (ablation honesty)

  • ExpertFlat (8:1 on both axes, 64 dense cols): fastest-ish (1.34×) but val 0.1102 — the coarsened router lost accuracy. This is the counterfactual that proves the decoupling thesis.
  • Sparse gather (only gather the ~16 selected blocks): ~5× slower than dense on CPU — per-query indexing + bmm kills cache locality.
  • Hierarchical / multi-scale pyramid compressors: extra params, no accuracy gain.
  • Linear-pool indexer: worse routing signal than the two-series overlap gate.
  • Stacked (2 blocks of attention): 0.1116 val — deeper but worse.
  • FlatPlus / Modified: hyperparameter variants that did not move the needle.
  • torch.empty bug: uninitialized bias memory (up to 10²⁸) on macOS caused NaN in softmax gates — fixed with torch.zeros.

# 3) Reliable speed comparison — ALWAYS head-to-head, alternating:
The #1 reproduction trap: CPU benchmark variance. Single sequential runs are unreliable — Flat has measured 29.7–45.3 ms with no code change, and one run under load-19 showed 273 ms. Use the alternating head-to-head harness below, and keep the machine quiet (this machine also runs backups from /Volumes/X9 that skew timings).
# benchmark_speed_head_to_head.py — the authoritative harness
import torch, time
from attention import CSAAttention
from expert_plus_plus_attention import ExpertPlusPlusAttention

torch.manual_seed(0)
B, S, D = 32, 256, 128
x = torch.randn(B, S, D)
flat = CSAAttention(hidden_size=D, num_heads=4, head_dim=32, q_lora_rank=64,
                    compress_rate=4, index_topk=16, sliding_window=32)
epp  = ExpertPlusPlusAttention(hidden_size=D, num_heads=4, head_dim=32, q_lora_rank=64,
                    compress_rate=8, index_compress_rate=4, index_topk=16,
                    sliding_window=16, o_groups=4, o_lora_rank=64)

def timeit(m, n=100):
    with torch.no_grad():
        for _ in range(20): m(x)          # warmup
        t0 = time.perf_counter()
        for _ in range(n): m(x)
        return (time.perf_counter() - t0) / n * 1e3   # ms

# alternating: A B A B ... — cancels thermal drift
ts_f, ts_e = [], []
for _ in range(10):
    ts_f.append(timeit(flat)); ts_e.append(timeit(epp))
print(f"Flat {sorted(ts_f)[5]:.2f} ms  |  EPP {sorted(ts_e)[5]:.2f} ms  "
      f"|  speedup {sorted(ts_f)[5]/sorted(ts_e)[5]:.2f}x")
#   → expect ≈ 29.7 ms vs 22.4 ms ≈ 1.32×

Gotchas

  • Shared-Q routing requires head_dim == index_head_dim (both 32 here). If you change one, EPP breaks.
  • GroupedLinear param counting: implemented as ONE nn.Linear(out, in_per_group) reshaped to (n_groups, out/n_groups, in_per_group) — params = out × in_per_group, NOT × n_groups. Naive per-group reimplementation double-counts.
  • Sentinel edge case: at q = S−1, ⌊t/2⌋ could map a sentinel to a valid block. EPP guards with an explicit torch.where(sentinel, n_kv, kv_blocks) — keep it.
  • Use torch.zeros for learnable biases — uninitialized macOS memory caused 10²⁸-scale NaNs in softmax gates.
  • z-score is over the ENTIRE series in dataset.py (not train-only) — keep identical for reproduction.
  • Window 32→16 was free accuracy (0.1099 both ways, better test) — but re-verify if you change S.
